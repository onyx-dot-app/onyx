## Local Deployment (Docker)

You can control the resources available to Docker in the **Resources** section of the Docker Desktop settings menu.

<Info>
  Often old, unused Docker images take up sizeable disk space. To clean up dangling images, run `docker image prune`.
</Info>

## Cloud Providers (AWS, GCP, etc.)

For small to mid scale deployments, we recommend deploying Onyx to a single instance in your cloud provider of choice.

### Onyx Lite

| Provider | Recommended Instance Type |
| --- | --- |
| AWS | `t3.medium` |
| GCP | `e2-medium` |
| Azure | `B2s` |

### Onyx Standard

| Provider | Recommended Instance Type |
| --- | --- |
| AWS | `m7g.xlarge` |
| GCP | `e2-standard-4` or `e2-standard-8` |
| Azure | `D4s_v3` |
| DigitalOcean | Meet the preferred resources in the table above |

## Container-Specific Resourcing (Standard)

For more efficient scaling, you can dedicate resources to each Onyx container using Kubernetes,
such as AWS EKS or Google GKE. The [Terraform modules](/deployment/local/terraform) for AWS, GCP,
and Azure include node pool sizes for small, medium, and large deployments.

See the [Onyx Helm chart](https://github.com/onyx-dot-app/onyx/blob/main/deployment/helm/charts/onyx/values.yaml)
`values.yaml` for our default requests and limits.
The chart's [sizing guide](https://github.com/onyx-dot-app/onyx/blob/main/deployment/helm/charts/onyx/SIZING.md)
has small, medium, and large values snippets.

| Component | CPU | Memory |
| --- | --- | --- |
| `api_server` | 1 | 2 Gi |
| Background workers (all `celery_*` workers) | 2 | 8 Gi |
| `indexing_model_server` | 2 | 4 Gi |
| `inference_model_server` | 2 | 4 Gi |
| `postgres` | 2 | 2 Gi |
| `opensearch` | 2 | 4 Gi |
| `nginx` | 250m (1/4) | 128 Mi |

<Info>
  If you are using cloud-based embedding models (e.g. OpenAI, Cohere, etc.) instead of locally hosted ones,
  the `indexing_model_server` and `inference_model_server` will use significantly less memory.
</Info>

All together, this comes out to a total available node size of at least ~12 CPU and ~24GB of Memory.

## Container-Specific Resourcing (Lite)

Docker Compose Lite starts six services. File storage, cache data, and sessions use PostgreSQL.

| Component | CPU | Memory |
| --- | --- | --- |
| `api_server` | 1 | 1 Gi |
| `web_server` | 250m (1/4) | 512 Mi |
| `postgres` | 1 | 1 Gi |
| `nginx` | 250m (1/4) | 128 Mi |
| `code-interpreter` | 100m | 512 Mi |
| `mcp_server` | 250m (1/4) | 256 Mi |

<Info>
  Memory usage in Lite mode scales with the number of user-uploaded files, since PostgreSQL handles file storage,
  caching, and session management. The code interpreter can use additional resources when it runs code.
  Helm Lite starts additional workloads unless you disable them explicitly;
  see the [Helm Lite configuration](/deployment/configuration/configuration#deploying-onyx-lite-with-helm).
</Info>

## OpenSearch Sizing

In Standard mode, OpenSearch is the component that grows with your data.
OpenSearch stores the indexed documents and runs the searches.
The other Onyx components keep the sizes in the tables above.

### Sizing Calculator

Use the calculator to estimate the OpenSearch storage, memory, and cluster size for your data.
Step 1 estimates what your data needs. Start from your total storage, from the item count of each source,
such as 2 million Google Docs, or from your number of employees. Step 2 puts that data on OpenSearch nodes.

<OpenSearchSizingCalculator />

The calculator divides your data into chunks. A chunk holds up to 512 tokens of text, about 1,900 characters.
For each chunk, OpenSearch keeps the text, its metadata, a keyword index, and one embedding vector.
Vector search reads the vectors from memory, so the memory need grows with the number of chunks and the embedding size.

| Value | Estimate | Basis |
| --- | --- | --- |
| Text per GB of storage | 40% for text files, 12% for office files, 8% for email, 5% for code, 4% for PDFs and slides | Estimate. Most mailbox storage is attachments and HTML. Onyx indexes only the documentation files in a code repository. |
| Chunks per item | 7 per document, 12 per PDF, 9 per slide deck, 10 per spreadsheet, 1 per image, 4 per wiki page, 2 per ticket, 1 per chat thread, 4 per email thread, 4 per CRM record, 12 per call, 6 per web page | Mean across Onyx Cloud tenants. Most items are smaller, but large ones set the total. The spreadsheet value is an estimate: Onyx indexes at most 24 chunks of a spreadsheet by default (`TABULAR_MAX_CHUNKS_PER_WORKBOOK`), and spreadsheets indexed with that limit average about 4 chunks. The estimate is higher to allow for large workbooks. Onyx makes one document from each chat or email thread. Change the value if you know your data. |
| Chunks per employee per year | 1,500 | Estimate from managed deployments, which range from about 200 to 1,500. Each year, one employee adds about 50 files (500 chunks), 100 email threads (400), 300 chat threads (300), 50 tickets (100), 25 wiki pages (100), and 100 chunks from other sources. If every employee's email is indexed, email is about 4,000 chunks instead of 400, so the rate becomes about 5,100. Older years usually add less than recent ones, so a long history errs on the high side. |
| Memory for vector search | Node RAM minus the JVM heap | The heap uses half of the RAM, at most 31 GB. The calculator counts 80% of the rest for vectors. |
| Memory per data node | 64 GB or less | The JVM heap stops at about 31 GB. For more data, add nodes instead of larger nodes. |
| Disk fill | 75% | OpenSearch stops placing shards on a node at 85% disk use |
| Shard size | 15 GB or less | Amazon OpenSearch Service recommends 10 GB to 30 GB per shard for search workloads. The calculator aims low so the index can grow without a change of shard count. |

<Note>
  The calculator gives a planning estimate. Real chunk counts depend on your documents. Each short document,
  such as a chat thread or a ticket, uses at least one chunk, so many short documents raise the count.
  Total storage counts no chunks for images. Onyx indexes each image as one chunk, so if you index many images,
  use Each source. After the first indexing run, compare the estimate with the index size that OpenSearch reports.
</Note>

### Memory

OpenSearch uses memory in two parts: the JVM heap and the OS file cache. The heap runs indexing and searches.
The file cache keeps index files in memory. Vector search reads the embedding vectors from the file cache,
so the file cache must hold the vector memory that the calculator shows.

For self-managed OpenSearch, set the heap with `OPENSEARCH_JAVA_OPTS` (Docker Compose) or `opensearchJavaOpts` (Helm):

- Set `Xms` and `Xmx` to the same value, at most 50% of the node's RAM.
- Keep the heap at or below 31 GB. Above about 32 GB, Java turns off compressed object pointers, and performance drops.
- When you give OpenSearch more RAM, raise the heap setting to match. The defaults are 2 GB (Docker Compose)
  and 4 GB (Helm).

Amazon OpenSearch Service sets the heap for you.

### Storage

OpenSearch storage depends on the number of chunks and the embedding model, not on the size of your files.
Most file bytes are images, fonts, and layout, and Onyx does not index them.

| Part of each chunk | Size |
| --- | --- |
| Text, metadata, keyword index, and graph links | About 2,650 bytes |
| Embedding vector | 4 bytes × dimensions |
| Quantized vector (7-bit or 1-bit) | Adds 1 byte or 1 bit per dimension. The full vector stays on disk. |

Indexes created before Onyx 5.0 also store a title vector,
so they use up to twice the vector storage until a reindex builds a new index.
A later release stops storing a second copy of the text and saves about 500 bytes per chunk.

Each copy of the data uses this storage again. Keep room for a second index:
a change of embedding model or quantization builds a new index while the old one serves search.

<Warning>
  OpenSearch stops placing shards on a node at 85% disk use and makes indexes read-only at 95%.
  Amazon OpenSearch Service blocks writes when a node has less than 20% or 20 GiB free, whichever is smaller.
  Deletes are blocked too, so you cannot free space from Onyx. Add storage before a node reaches 85%.
</Warning>

To see the real size of your index, run this request against OpenSearch:

```
GET _cat/indices/danswer_chunk*?v&h=index,docs.count,pri.store.size,store.size
```

`docs.count` is the number of chunks. `pri.store.size` is the size of one copy.

### When to Scale

| Signal | Action |
| --- | --- |
| Disk use on a node is above 75% | Add storage or data nodes |
| Search is slow and JVM heap use is low | Add memory or data nodes, or use 1-bit quantization (OpenSearch 3.6 or later), which stores vectors 32× smaller |
| JVM heap use stays above 75%, or requests fail with `CircuitBreakingException` | Raise the heap, up to 50% of the node's RAM and at most 31 GB. Raise the container memory limit too. |
| Shards grow above 30 GB | Plan a reindex with a higher `OPENSEARCH_INDEX_NUM_SHARDS` |

You can add data nodes, storage, memory, and replicas later without a reindex.
The number of primary shards is fixed when Onyx creates the index. To change it, Onyx must build a new index.

### Example

500 GB of storage with the default storage mix holds about 35 GB of text, or 18.5 million chunks. With 30% growth,
the calculator plans for 24 million chunks.

| Setup | Index size, one copy | Memory for vector search, one copy | Cluster | Onyx settings |
| --- | --- | --- | --- | --- |
| Granite (384 dimensions), 2 copies | 106 GB | 37.8 GB | 3 nodes, 64 GB RAM and 256 GB storage each | `OPENSEARCH_INDEX_NUM_SHARDS=9`, `OPENSEARCH_INDEX_NUM_REPLICAS=1` |
| Same, with 1-bit quantization | 107 GB | 2.1 GB | 2 nodes, 16 GB RAM and 512 GB storage each | `OPENSEARCH_INDEX_NUM_SHARDS=8`, `OPENSEARCH_INDEX_NUM_REPLICAS=1` |
| Granite, 1 copy | 106 GB | 37.8 GB | 2 nodes, 64 GB RAM and 256 GB storage each | `OPENSEARCH_INDEX_NUM_SHARDS=8`, `OPENSEARCH_INDEX_NUM_REPLICAS=0` |
| Same, with 1-bit quantization | 107 GB | 2.1 GB | 1 node, 16 GB RAM and 512 GB storage | `OPENSEARCH_INDEX_NUM_SHARDS=8`, `OPENSEARCH_INDEX_NUM_REPLICAS=0` |

The shard count makes the shard copies divide evenly over the nodes, so no node holds more than its share.
1-bit quantization needs OpenSearch 3.6 or later. It stores vectors 32× smaller,
so the memory for vector search drops about 18× in this example (the graph links stay the same size).
Storage barely changes.

Onyx applies both settings when it creates an index. To change the replica count of an existing index,
update the index setting `number_of_replicas` in OpenSearch.
