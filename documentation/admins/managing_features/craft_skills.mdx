Skills package reusable instructions and supporting files that teach Craft how to perform a kind of work.
Open **Admin Panel → Skills** to manage custom Skills across your organization.
Open **Craft → Skills** to manage your own library.

<Note>
  Anyone with Craft access can create a Skill and manage the Skills they own or can edit.
  Admins can inspect and manage all custom Skills, including private personal Skills.
  Global manage-skills permission controls company access and installation policies.
  Craft needs a Business or Enterprise plan, or Onyx Cloud.
</Note>

## Understand the Skills library

| Type         | Where it comes from            | What an admin can do                                                                    |
| ------------ | ------------------------------ | --------------------------------------------------------------------------------------- |
| **Built-in** | Shipped and maintained by Onyx | Preview its instructions and identify missing dependencies. Built-ins are not editable. |
| **Custom**   | Created by an admin or user    | Edit, share, set installation policy, manage files, enable or disable, transfer ownership, or delete. |

New custom Skills start private unless you configure access during creation or import. Share Skills with people, groups,
or the organization when others should use them.

The admin table shows each Skill's name, description, access, and installation policy.
Synced Skills also show their marketplace and repository folder. Open a row to preview the Skill.
App connection status appears separately from the Skill description. Use its **More actions** menu to edit, share,
or delete it. The **Enable for me** column controls your personal enablement. Required Skills have no switch.
On narrow screens, the column is named **For me**. Names can use two lines.
Duplicate names use one line and keep their descriptions. Use the **Add** plus button beside the title to create,
upload, or sync Skills. Open **Edit sharing** for access and installation settings.

## Manage several Skills

<Steps>
  <Step title="Select the Skills">
    Open **Admin Panel → Skills** and use the checkboxes on the custom Skill rows.
    Use the checkbox in the table header to select all visible custom Skills. Search first to limit the selection.
    For a nonempty list, the count below search shows the number of matching custom Skills, then the number selected.
    Search and bulk controls stay visible when you scroll the list. Bulk actions appear beside the count,
    or below it when space is limited. A loading indicator beside the count shows when a bulk change is in progress.
    A checked box marks a selected Skill. Keyboard focus alone does not select it.
  </Step>

  <Step title="Configure access and installation">
    Select **Share**. Choose **Everyone in the organization** to share all selected Skills with your staff.
    You can also add specific people or groups. People and groups you list get the chosen permission.
    Other existing grants remain in place. Settings left at **Keep unchanged** retain their current values.
  </Step>

  <Step title="Apply the changes">
    Select **Apply** to update the selected Skills.
    Onyx lists each failure below the controls and moves keyboard focus to the alert.
    Failed Skills stay selected so you can retry them.
  </Step>
</Steps>

**Enable for me** and **Disable for me** change your personal library only.
Use **Installed by default** or **Required** under **Installation** to deploy Skills to people with access.
Open **More actions** for personal enablement and deletion. **Delete** removes selected Skills for everyone with access.
The confirmation lists each selected Skill before deletion.

### Set access during import

Select **Add** > **Sync from GitHub** to preview a marketplace catalog.
Global skill managers can select **Company Marketplace** and set organization access, installation, and group defaults.
The initial defaults are organization Viewer access, Available installation, and no groups.
Switching to private and back keeps your selected organization permission until you close the dialog.
Onyx saves the source and its selected defaults together before requesting its first sync.

You can also select several ZIP files in **Upload a skill**. Each ZIP must contain one Skill.
Configure access once before importing the batch. Onyx reports invalid bundles separately.

### Built-in Skills

| Skill                | Availability                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| **Presentations**    | Available with Craft and provides the workflow for creating and validating `.pptx` files.        |
| **Company search**   | Available with Craft and searches Onyx knowledge using the current user's document permissions.  |
| **Browser**          | Available when the deployment's browser runtime is enabled.                                      |
| **Image generation** | Available after an admin configures a supported [image model](/admins/actions/image_generation). |
| **Craft documentation** | Available with Craft and helps Craft answer questions about itself. |
| **App Skills**       | One per App, such as Slack, Gmail, Google Drive, GitHub, Linear, Notion, HubSpot, or Zendesk. Available after the user connects the [App](/admins/plugins/craft_apps). |

An unavailable built-in remains visible to Admins with the reason it cannot be used.
Configure the missing dependency rather than uploading a custom Skill with the same slug.

## Prepare a custom Skill

You can write a Skill in Onyx, upload a Skill, or import Skills from a GitHub repository.
Upload `SKILL.md` directly when the Skill does not need supporting files. For a Skill with scripts, examples,
or other supporting files, create a folder with `SKILL.md` at its top level. Drag the folder into Onyx,
or upload it as a ZIP.

<Info>
  For a standalone `SKILL.md`, Onyx creates the slug from the frontmatter `name`. For a folder,
  the folder name becomes the slug. For a ZIP, the filename without `.zip` becomes the slug.
  Folder and ZIP names must start with a lowercase letter, contain only lowercase letters, numbers, and hyphens,
  and be no more than 64 characters. Slugs must be unique. If an existing Skill already uses the slug,
  update that Skill or change the source name before uploading.
</Info>

```text
weekly-customer-update/
├── SKILL.md
├── examples/
│   └── finished-update.md
├── templates/
│   └── update-template.md
└── scripts/
    └── validate.py
```

For a ZIP upload, put `SKILL.md` at the archive root or directly inside one enclosing folder.
When you use an enclosing folder, keep every Skill file inside it.

`SKILL.md` must begin with YAML frontmatter containing a non-empty name and description.
The description should state when Craft should choose the Skill.

```md
---
name: weekly-customer-update
description: Create a weekly customer update from account activity and meeting notes.
---

# Weekly customer update

1. Summarize material changes since the previous update.
2. Separate decisions, risks, and next steps.
3. Name an owner and due date for each next step.
4. Follow `templates/update-template.md`.
5. Run `scripts/validate.py` before returning the final file.
```

Craft reads a relative path such as `scripts/validate.py` from the Skill folder.
A command can also use `${CLAUDE_SKILL_DIR}`, as in `python ${CLAUDE_SKILL_DIR}/scripts/validate.py`.
Craft replaces `${CLAUDE_SKILL_DIR}` in `SKILL.md` with the Skill folder before the agent reads it.
The stored `SKILL.md` keeps the variable. If expansion exceeds the file limit or the sandbox delivery limit,
Craft skips that Skill and logs a warning. The saved bundle stays unchanged. Other Skills remain available.

### Bundle requirements

| Requirement         | Default                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Slug                | Generated from the Skill name when written in Onyx or uploaded as `SKILL.md`; otherwise, the folder name or ZIP filename without `.zip`.     |
| Root instructions   | One UTF-8 `SKILL.md` with valid YAML frontmatter at the Skill root.                                                                         |
| Skills per ZIP      | One. Select multiple ZIP files to import a batch.                                                                                            |
| Maximum ZIP size    | 25 MiB for the ZIP file.                                                                                                                     |
| ZIP file-list size  | 1 MiB, including entry names, extra fields and comments. |
| Maximum file count  | 500 files. Folders do not count.                                                                                                            |
| Maximum file size   | 25 MiB per file in the extracted bundle.                                                                                                     |
| Maximum bundle size | 100 MiB total in the extracted bundle.                                                                                                       |

Onyx checks each limit separately and counts the bytes that it extracts.
The file count includes metadata that Onyx removes: `__MACOSX/`, `.DS_Store`, `Thumbs.db`, and `._*` files.
Folders do not count. The ZIP limit applies to both the uploaded ZIP and the ZIP that Onyx stores after normalization.
Standalone files use the per-file limit before compression.
Each Skill from a GitHub repository must also pass these limits.
Single-bundle uploads over a limit return HTTP 413 with `limit` and `limit_value`.
Batch uploads and GitHub imports can return HTTP 200 with rejected Skills in `not_imported`,
with a `reason` for each refusal.
Repository-wide GitHub size checks can reject the whole request with HTTP 413 before individual Skills are inspected.
Previously saved Skills keep the existing per-file and expanded-total limits.
Lowering the upload ZIP-size or file-count limit does not change stored-bundle validation.
Stored ZIP reads default to `SKILL_BUNDLE_TOTAL_MAX_BYTES` (100 MiB unless configured).
Set `SKILL_BUNDLE_STORED_ZIP_MAX_BYTES` to choose a separate stored ZIP allowance.
Keep this allowance large enough for your existing bundles when you lower upload limits.
An existing expanded-total setting above 100 MiB also preserves that stored ZIP allowance after upgrading.
A saved bundle above this allowance returns a 413 read-limit error. Raise the allowance to read it.
Stored reads have no file-list size limit. Onyx applies the current upload limits when you save the Skill again.

Self-hosted operators can change the limits with `SKILL_BUNDLE_ZIP_MAX_BYTES`, `SKILL_BUNDLE_MAX_FILE_COUNT`,
`SKILL_BUNDLE_PER_FILE_MAX_BYTES` and `SKILL_BUNDLE_TOTAL_MAX_BYTES`. If your reverse proxy sets a request size limit,
allow space for the bundle and multipart form data.
The effective upload ZIP limit cannot exceed the stored ZIP allowance. Raise both settings to accept larger ZIPs.
ZIP size errors show the exact configured limit. Values that are not whole MiB are shown in bytes.

The upload is rejected when the bundle has unsafe paths, symbolic links, files ending in `.template`,
missing or invalid frontmatter, an invalid slug source, a duplicate Skill slug,
or a slug reserved by a built-in Skill or App.

## Review a Skill before publishing

Treat a Skill bundle as code and policy, not only as prompt text.
Craft can follow scripts and commands included in the archive.

| Review area                | What to check                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Purpose and selection**  | The name and description clearly identify when the Skill should and should not be used.                            |
| **Instructions**           | The workflow is bounded, internally consistent, and does not tell Craft to evade approvals or organization policy. |
| **Scripts**                | Every executable file is expected, readable, and safe to run on user-provided or company data.                     |
| **External access**        | The bundle contains no embedded tokens and uses a configured App for authenticated services.                       |
| **Examples and templates** | Included files contain no confidential data and represent the quality users should expect.                         |
| **Output handling**        | The Skill names the expected format and writes finished deliverables to a clear location such as `outputs/`.       |

<Warning>
  Never publish a bundle containing passwords, API keys, OAuth tokens, private certificates, or production credentials.
  Skill files are copied into the sandboxes of users who can access the Skill. Use [Apps](/admins/plugins/craft_apps)
  for authenticated external access.
</Warning>

## Publish a Skill

Admins create Skills through the same personal creation flow as other users.
Publishing means reviewing that Skill and then sharing it with the intended audience.

<Note>
  Sharing a Skill with the whole organization requires being its author or an Admin.
  You can delete any Skill you own or can edit, and Admins can delete any custom Skill.
</Note>

<Steps>
  <Step title="Create the personal Skill">
    Open **Craft → Skills** and select **Add**. Choose **Create a skill** to write the Skill in Onyx,
    **Upload a skill** to import `SKILL.md`, a ZIP, or a Skill folder,
    or **Sync from GitHub** to add a marketplace source. Uploaded and authored Skills support sharing in the editor.
  </Step>

  <Step title="Review the Skill">
    Review the name, description, rendered instructions, and supporting-file tree.
  </Step>

  <Step title="Choose who can use it">
    Select **Edit sharing**. Under **Who can access**,
    share with the organization or use **Manage individual access** to grant **Can use** to specific users or groups.
    Grant **Can edit** only to people who maintain the Skill. Under **Installation**,
    choose how the Skill is installed for everyone with access.
  </Step>

  <Step title="Test with the intended audience">
    Start a Craft session as a user in the target audience, select the Skill, and test representative inputs,
    missing-data cases, and the final output.
  </Step>
</Steps>

## Choose sharing permissions

| Scope               | Can use                                                   | Can edit                                                                                 |
| ------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **Specific people** | Selected users can use and preview the Skill.             | Selected users can also modify and manage the Skill.                                     |
| **Groups**          | Members of selected groups can use and preview the Skill. | Members can also modify and manage the Skill.                                            |
| **Organization**    | Everyone can use and preview the Skill.                   | Everyone can modify and manage it. Use this only for intentionally collaborative Skills. |

Users with **Can edit** can change instructions and files, update sharing within their permissions,
enable or disable the Skill, and delete it.

<Tip>
  Prefer organization-wide **Can use** access with a small maintainer group that has **Can edit**.
  This keeps the Skill broadly usable without making its behavior broadly editable.
</Tip>

An uploaded Skill associated with an App stays visible to the organization.
Company marketplace Skills keep their access settings when linked to an App.

For uploaded Skills and company synced Skills, company visibility changes require global manage-skills permission,
including changes by the owner. Owners without that permission can still share with individual users.
Group sharing follows the user's group permissions.
Editing instructions or individual access preserves existing organization access.
If another edit changes the Skill while you edit instructions or files, retry your edit.
The conflict leaves the other edit in place. Onyx checks your edit permission again before saving.
Group managers can change sharing only within the groups they manage. For Skills without an owner,
group managers can edit group access. Individual user grants require global manage-skills permission.

## Choose an installation policy

Users with global manage-skills permission set how a shared Skill is installed for everyone with access:

| Policy | Effect |
| --- | --- |
| **Available to install** | Users can install or uninstall the Skill at any time. |
| **Installed by default** | Onyx installs it automatically. Users can disable or uninstall it. |
| **Required** | Onyx selects it automatically. Users cannot turn it off directly. Name conflicts still follow library priority below. Deleting it requires global manage-skills permission. |

The policy follows the current audience; changing who can access the Skill does not reset it.
Bulk sharing preserves existing grants and group install settings that the request omits. In the sharing API,
an omitted group `installation_policy` preserves its value; explicit `null` clears the override.
Each group without an override inherits the organization setting. For users in several shared groups,
**Required** takes precedence over **Installed by default**, then **Available to install**.
Users outside those groups use the organization setting.
Changing installation settings keeps each user's saved on/off preference, but can change which same-name Skill loads.
For example, an opt-out returns when a group changes from **Required** back to **Installed by default**.
When you add users to a group or remove them, Onyx requires updated sandbox Skills before admitting another message.
If Onyx cannot update a sandbox, the message fails and asks the user to try again.
A message already admitted when membership changes can continue, even if its network send starts after the change.
If a Skill delivery blocks the membership update, Onyx rejects the complete update with a retry message.
This can occur while Onyx delivers Skills from your previous membership update. Admin requests return HTTP 409.
SCIM requests return HTTP 503 in the SCIM error format, with a one-second `Retry-After` header.
Retry the membership update after the delivery finishes. Repeated deliveries can require more than one retry.
Retired Skills reject changes other than deletion.

A new custom Skill cannot use a live Skill's name in the same library: the company library or one user's library.
Upload a new version to update an existing Skill. Its name must stay the same.
Different libraries can use the same name. A sync blocks a conflicting new entry and keeps existing content.

When enabled Skills share a name, Onyx loads one. A company Skill takes precedence over your own Skill,
and your own Skill takes precedence over a Skill shared by another user. The oldest Skill wins a tie. Disabled Skills,
invalid bundles, removed built-ins, and Skills with disconnected apps do not hide a usable Skill.
This order also applies to Required Skills and saved choices. A company Default can hide your explicitly enabled Skill.
Your own enabled Skill can hide a Required Skill shared by another user. The saved choices remain in place.
If a bundle cannot load, Onyx tries the next eligible Skill in the same order.
The Skills API identifies duplicates with `hidden_reason: "same_name"` and the selected Skill's `hidden_by_skill_id`.
These fields use saved validity information.
A temporary storage failure can change the delivered Skill without changing these fields.

## Maintain a Skill

Open a custom Skill to manage its lifecycle:

| Action                 | Effect                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Edit details**       | Updates the name, description, or Markdown instructions and rewrites `SKILL.md` in the stored bundle.                              |
| **Add files**          | Adds files, folders, or unpacked ZIP contents. A file at an existing path replaces the stored file.                              |
| **Remove files**       | Removes a supporting file from the bundle. `SKILL.md` cannot be removed.                                                          |
| **Replace content**    | Uploading content with `SKILL.md` replaces the name, description, instructions, and complete bundle after confirmation.           |
| **Disable**            | Prevents Craft from using the Skill without deleting its configuration or sharing.                                                 |
| **Edit sharing**       | Changes who can use or edit the Skill and how it is installed.                                                                     |
| **Transfer ownership** | Assigns responsibility to another active standard user.                                                                            |
| **Delete**             | Permanently removes the Skill, its version history and its stored bundles.                                                         |

Changes are synchronized to affected running sandboxes.
A turn already in progress may have loaded the previous instructions,
so validate important changes in a new turn or session before announcing them.

### Ownership

Every custom Skill has one owner. The owner can transfer it to another active standard user.
If ownership becomes vacant because the owner is inactive, a user with global manage-skills permission can transfer it.

Do not transfer ownership to bots, service accounts, limited accounts, or inactive users.

### Version history API

Owners, editors, and admins can read and restore custom Skill versions through the API. Viewers cannot list, preview,
or restore historical versions. These requests return `404` for users without edit access.
Built-in Skills do not have version history. For retired Skills,
only the personal owner or a global Skill manager can read history. Restore remains unavailable.
A Personal Access Token must include Manage Skills to use global management authority.

Use a [Personal Access Token](/developers/overview) with access to the Skill:

```bash
curl "$ONYX_URL/api/skills/custom/$SKILL_ID/versions" \
  -H "Authorization: Bearer $ONYX_TOKEN"
```

The response lists up to 50 versions from newest to oldest. Each entry contains `id`, `version_number`, `created_at`,
`created_by`, `is_current`, `has_bundle`, and `marketplace_revision`.
`created_by` contains the creator's `id` and `email`, or `null` when that information is unavailable.
`marketplace_revision` identifies the source commit for a synced version; it is `null` for other versions.
To read the next page, set `before_version` to the last entry’s `version_number`. The cursor must be a positive integer.
Stop when the response is empty or includes version 1. New versions do not shift older pages.
Skill list and detail responses include `current_version_number`,
which is `null` for built-ins and custom Skills that have no version.
Older servers can omit this field during an upgrade.
The library hides the version label until version data is available.

| Method | Path after `/api` | Result |
| --- | --- | --- |
| `GET` | `/skills/custom/{skill_id}/versions` | Version history, including versions whose files were removed. |
| `GET` | `/skills/custom/{skill_id}/versions/{version_id}` | Historical name, description, instructions, and supporting-file paths and sizes. |
| `POST` | `/skills/custom/{skill_id}/versions/{version_id}/restore` | Restored Skill details, instructions, and supporting-file list. No request body is needed. |

Restore copies the selected content into a new version and updates the Skill description. It preserves ownership,
sharing, and installation settings. Identical content does not add a version.
Restored content must pass the current bundle validation and upload limits.

Onyx keeps files for the newest ten versions, including a newly restored version. Older entries remain with `has_bundle:
false`. Preview and restore return `404` with "The files of this version are no longer kept." if the bundle is absent.
A version ID from another Skill also returns `404`.

## Synced marketplace Skills

Both Skills pages show **Marketplaces** above the library. Open a source to inspect status, errors, and Skills.
**Request sync** saves work for the background worker. The list refreshes until the worker finishes.
A failed or pending source remains visible even when it has no Skills. Use **Sync now** for another request,
or **Replace login** to use your connected GitHub account.
Company managers can open the source's access settings to change defaults for following Skills.

Synced Skills show their marketplace name and repository folder in the library.
Owners and editors can select **View content** to read instructions and inspect the file list.
The content page is read-only. To change instructions or files, edit the GitHub repository and sync the marketplace.
Permitted sharing settings remain available. Active synced Skills cannot be deleted from row actions or bulk selection.

Skill list and detail responses include `marketplace` for synced Skills and `null` for other Skills.
It contains the source `id`, `name`, `personal` scope, Skill `folder`, and `follows_access` flag.
The folder is relative to the repository root. The response does not include source credentials or login details.
For company sources, `follows_access` indicates whether marketplace default changes apply to this Skill.
`marketplace.can_share` indicates whether the current user and token can open sharing controls for a synced Skill.
It includes group scope even when the response omits group details. Every write checks authority again.

Change a synced Skill's instructions and files in its GitHub repository. Onyx rejects manual content changes,
version restores, ownership transfers, and deletion while the synced Skill remains active.
You can still change permitted sharing settings and enable the Skill for yourself. Required Skills cannot be disabled.

When sync retires a Skill, it disappears from libraries, App skill lists, and future sandbox skill payloads.
Its name becomes available for another Skill. Existing sessions use the normal reload flow to receive skill changes.
Retirement preserves version history for internal retention and cleanup.
Retired Skills reject all user changes except deletion. To delete one, open its marketplace under **Marketplaces**.

<img className="rounded-image" src="/assets/admins/managing_features/retired_skill_versions.webp" alt="Read-only version history for a retired Skill, with Preview and Back to marketplace actions"/>

Retired Skills show a **Retired** badge, read-only **Versions**, and a **Delete** action. Select **Delete**,
review the named Skill, then confirm. Deletion permanently removes the Skill and its version history.
Only the personal owner or a global manage-skills user can delete a retired synced Skill.
An editor grant alone does not permit deletion. The same rule applies to bulk deletion.

Open **Edit sharing** to see whether a company Skill **Follows Marketplace Access** or uses **Custom Access**.
Saving an access or installation change creates custom settings for that Skill.
Global skill managers can select **Reset to marketplace access**, then **Reset access**.
Reset removes individual grants, discards unsaved changes, and restores the source defaults.
Future marketplace access changes then apply to the Skill.

Only the owner can change a personal synced Skill's audience, including company visibility and group grants.
This also applies when the owner is a group manager.
Changing installation settings still requires the appropriate manage-skills authority.
Other editors and admins cannot change that audience.
A manager can change installation settings while preserving the existing grants.
API tokens need manage-skills scope to use management authority. This applies to reads, sharing, creation, import,
content, version history, enable, ownership transfer, and deletion.
Creating a Skill for an App also requires full-admin token scope.
A Basic-only token retains the user's ownership and explicit editor grants.
It cannot use the user's admin or group-manager role to change installation settings or company access.

## Manage marketplaces through the API

Management responses include `sync_pending` while work is queued or claimed by a worker.
Use this field to keep polling until the sync finishes. `sync_requested` becomes false when a worker claims the request.

Use `POST /api/marketplaces/preview` to check a source before adding it. Connect your GitHub account first.
For a personal source, send:

```json
{
  "provider": "github",
  "provider_config": {
    "owner": "acme",
    "repo": "agent-tools",
    "ref": "main",
    "folder": "catalog"
  },
  "personal": true
}
```

Omit `folder` when the marketplace file is at the repository root. The ref can be a branch, tag, or commit.
Set `personal` to `false` for a company source. Company previews require global permission to manage Skills.

A complete preview returns the resolved revision and entries marked `ok`, `blocked`, or `not_supported`.
Ready entries include a name and description. Other entries include a reason.
A missing or invalid marketplace file returns `status: "failed"` with a reason.
Preview does not save a marketplace or upload bundles. It validates source content;
sync still checks library name conflicts and the source's current revision.

To add the source, send the same fields and a non-empty `name` to `POST /api/marketplaces`.
Onyx validates the current source again, saves the marketplace, and requests its first background sync.
An invalid marketplace file prevents creation. Blocked and unsupported entries do not prevent creation.
For a company source, include `access` with the same fields as the access route below.
Onyx saves these defaults with the source before starting its first sync. Invalid defaults prevent creation.
Personal sources do not accept `access`.

Use `GET /api/marketplaces` to list sources you can manage. Use `GET /api/marketplaces/{marketplace_id}` for its Skills,
including retired Skills. Owners can read personal sources. Global manage-skills users can read all sources.
A token restricted to Basic access can read only its owner's personal sources. Responses include sync status,
blocked entries, default access, and live and retired Skill counts. They exclude credentials.

Use these routes to manage a saved source:

| Route | Effect |
| --- | --- |
| `POST /api/marketplaces/{id}/sync` | Request a background sync. |
| `POST /api/marketplaces/{id}/replace-login` | Validate and use your connected GitHub account for future syncs. Preserve Skill IDs, history and shares. |
| `POST /api/marketplaces/{id}/confirm-retirements` | Approve the exact pending retirement proposal. |
| `PATCH /api/marketplaces/{id}/access` | Set company and group defaults for a company marketplace. |
| `DELETE /api/marketplaces/{id}` | Permanently delete the marketplace, its Skills and their history. |

The owner or a global manage-skills user can sync, replace login, confirm or remove a personal source.
Company operations and default access changes require global manage-skills permission.
Token scopes must also allow the operation.
An admin can remove a deactivated user's personal sources before deleting that user.

Confirmation takes `revision` and `skill_ids` from the current `retirement_proposal` in the detail response.
Confirm only when `sync_status` is `needs_confirmation`. A changed proposal returns a conflict. After a failed sync,
run sync again before confirming a preserved proposal.

Access changes use `public_permission`, `installation_policy`, and `group_shares`, as in the Skill sharing API.
Each group share has `group_id`, `permission` (`VIEWER` or `EDITOR`), and an optional `installation_policy`.
Omitted settings stay unchanged. An explicit `null` group installation policy clears that override.
Personal marketplace Skills are shared individually; marketplaces do not accept direct user grants.
Company default changes apply only to Skills that follow marketplace access.

Sync requests return after saving the request. Read the detail route to check progress and errors.
If dispatch is temporarily unavailable, the saved request remains queued for recovery.

## Marketplace sync recovery

Marketplace sync runs in the background. A request made during a sync triggers another check,
so newer commits are not lost. Interrupted or queued requests recover automatically, including on Onyx Lite.
Onyx does not check idle marketplaces on a timer.
Temporary source errors and interrupted runs get at most three attempts per request.
Automatic retries wait at least one minute, then at least two minutes. The background schedule can add delay;
Onyx Cloud normally checks recovery about every four minutes. After three failed attempts, request a new sync.
An explicit request starts a fresh attempt budget and clears the retry delay.
Each attempt must finish saving its changes within five minutes after it starts. If that limit expires,
Onyx keeps the last successful content and applies the retry rules above.

Each sync requires an active login user with a connected GitHub account.
An unavailable login records an error and preserves existing Skills. A successful check clears an earlier error,
even when the source has not changed. Missing sources, invalid input, and login failures wait for an explicit request;
they do not retry automatically.
A failed source read or a retirement that needs confirmation preserves the last successful content.
An incomplete TAR archive fails the whole sync. If a plugin loses its root `SKILL.md` but retains other files,
Onyx marks that entry as blocked and keeps its saved Skill.
A different source revision clears the previous retirement approval. This applies even if saving the new content fails.
Returning to the earlier revision requires a new confirmation before a large retirement.
Sync saves its result with the updated Skills. A later sandbox delivery failure does not change that result.

## Reset marketplace Skill access through the API

Company marketplace Skills remain when their author or GitHub login user is deleted.
If the deleted user supplied the source's GitHub login, replace it to resume syncing.
Remove a user's personal marketplaces and transfer or delete their private uploaded Skills before deleting that user.

For a Skill from a company marketplace,
use `POST /api/skills/custom/{skill_id}/reset-marketplace-access` with no request body.
The request requires global permission to manage Skills and sufficient token scope.
It returns the Skill and its sharing details.

Reset removes individual user shares and restores the marketplace's company visibility, group access,
and installation settings. Later marketplace access changes apply to the Skill again.
Reset preserves content and version history. Personal marketplace Skills and retired Skills cannot use this endpoint.

## Before reverting automatic name resolution

Deployment operators must check for duplicate names before downgrading past migration `54013115725e`.
That downgrade restores a unique index on live Skills whose installation policy is not **Available to install**.
The current runtime allows those Skills to share a name across libraries. The older index does not.

Back up the database. Run this read-only query to find names that would prevent the downgrade:

```sql
SELECT name, array_agg(id ORDER BY id) AS skill_ids
FROM skill
WHERE installation_policy <> 'AVAILABLE' AND retired_at IS NULL
GROUP BY name
HAVING count(*) > 1
ORDER BY name;
```

For each result, decide which Skill can keep its current installation policy. In **Admin Panel → Skills**,
set the others to **Available to install** before the downgrade. Record those choices.
Do not change customer policies automatically or delete Skills to make the migration pass.
If several same-name Skills must keep another policy, do not downgrade past this revision.

Stop API servers, workers, and other writers before the final check and migration. Run the query again.
Continue only when it returns no rows. Keep writers stopped until the downgrade finishes.
This check does not replace other release-specific downgrade steps.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A Skill bundle will not upload">
    Confirm that the upload contains one Skill. `SKILL.md` must be at the top level of a folder. In a ZIP,
    place it at the archive root or directly inside one enclosing folder.
    Check that it uses UTF-8 and begins with valid YAML containing non-empty `name` and `description` fields.
    For a standalone `SKILL.md`, make sure `name` contains at least one letter or number. Otherwise,
    check the folder or ZIP name. Check the bundle limits, and remove symbolic links or unsafe paths.
  </Accordion>

<Accordion title="A built-in Skill is unavailable">
  Open its preview to read the unavailable reason. Configure Image Generation for the image Skill,
  or ask the deployment operator to verify the browser runtime for the Browser Skill.
  Built-in Skills cannot be replaced or enabled from the Skills editor.
</Accordion>

<Accordion title="Users cannot find a shared Skill">
  Confirm that the Skill is enabled and that the user or one of their groups has **Can use** or **Can edit** access.
  If it was shared during an active session, start a new turn or session and check the picker again.
</Accordion>

<Accordion title="Craft does not choose the Skill automatically">
  Rewrite its description to name the covered tasks and outputs more concretely. Test again,
  and have users select it explicitly when the workflow must be followed.
</Accordion>
</AccordionGroup>
