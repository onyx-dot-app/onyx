<Note>
  `/chat/send-message` and `/chat/send-message-simple-api` have been removed. Use this API instead.
</Note>

Use the `/chat/send-chat-message` API to send a message to Onyx.
It is the same API that the Onyx web app uses to send and receive messages.
You can receive a streaming response or one complete response.

<Note>
  Authenticate with an API key or a Personal Access Token. A limited-access token needs the **Chat &mdash;
  Write** scope. See [Authentication](/developers/overview#authentication).
</Note>

## Request Parameters

| Parameter | Description |
|-----------|-------------|
| `message` | The user message to send to the Agent. |
| `llm_override` | Pass an object to override the default LLM settings for this request. If `None`, you will get the default Onyx behavior. <br/><br/>You can pass or exclude any of the following fields: <br/>• `model_configuration_id` – the exact model configuration to use. Preferred over the name-based fields, since provider display names are not unique <br/>• `model_provider` <br/>• `model_version` – must match a model configured on the resolved provider. If it does not, the request is rejected with `INVALID_INPUT`: an HTTP `400` when `stream=false`, or an error packet with `"error_code": "INVALID_INPUT"` when streaming (the default). If no provider resolves, or you cannot use that provider, Onyx uses the default LLM instead. Onyx does not check `model_version` when you pass `model_configuration_id` <br/>• `temperature` <br/>• `display_name` – label shown for the model in the UI; falls back to `model_version` |
| `llm_overrides` | Two or three `llm_override` objects to run in parallel (multi-model mode), one per model. <br/><br/>**Requires `stream=true`.** Sending more than one entry with `stream=false` fails with `400 {"error_code": "INVALID_INPUT"}`. A list with a single entry is ignored — use `llm_override` for an ordinary single-model request. |
| `allowed_tool_ids` | Each Agent has a set of Actions (built-in tools, MCP Actions, and OpenAPI Actions from **Admin Panel** > **Plugins**) that it can invoke. Use this parameter to narrow that set for this request. List the Actions and their IDs with the [GET /tool](/developers/api_reference/actions/list_tools) endpoint. Pass an empty list to disable all Actions. Omit the field or pass `null` to allow every Action configured for the Agent. |
| `preferred_tool_id` | Prefer one Action when it helps answer this request. The Agent can use other Actions or answer without an Action. The preference lasts for this request only. |
| `file_descriptors` | A list of files to include with your request. Each entry is `{"id": ..., "type": ..., "name": ...}`. Upload files with [POST /user/projects/file/upload](/developers/api_reference/projects/upload_user_files) and read them back with [GET /user/projects/file/{file_id}](/developers/api_reference/projects/get_user_file). |
| `internal_search_filters` | Filters to narrow down the internal search results used by the Agent. All filter arguments are optional and can be combined: <br/><br/>• `source_type` – Source types like `web`, `slack`, `google_drive`, `confluence` <br/>• `document_set` – The name of the document sets to search within <br/>• `created_at_range` / `updated_at_range` – An inclusive window, `{"start": ..., "end": ...}`, in ISO 8601 format: `YYYY-MM-DDTHH:MM:SSZ`. Either bound may be omitted to leave that side open; naive timestamps are treated as UTC <br/>• `tags` – A list of `{"tag_key": ..., "tag_value": ...}` objects <br/><br/>**Note:** `time_cutoff` is still accepted as a deprecated alias for the start of `updated_at_range`. |
| `deep_research` | Enables Deep Research mode for this request. <br/><br/>**Note:** This mode uses many more tokens than a normal request. |
| `mcp_headers` | Headers forwarded to MCP tool calls made while answering this message, e.g. `{"Authorization": "Bearer <user_jwt>"}`. Use this to pass end-user credentials through to MCP servers that require them. |
| `parent_message_id` | The ID of the parent message in the chat history. Omit it (or pass `-1`) to place the new message after the latest message in the session. Pass a specific message ID to branch from that point. <br/><br/>**Warning:** If set to `null`, the new message starts from the root of the session, as the first message. |
| `chat_session_id` | To continue an existing conversation, pass the chat session ID. If left blank, Onyx creates a new chat session from `chat_session_info`. Pass only one of `chat_session_id` and `chat_session_info`. |
| `chat_session_info` | Settings for a new chat session. They apply to every message in the session. Leave fields blank to use defaults. <br/><br/>• `persona_id` – The ID of the Agent to use. Defaults to `0`, the default Agent <br/>• `project_id` – ID of a Project if the chat should be scoped to a Project <br/>• `incognito` – Start the session in incognito mode. The request fails with an error when incognito is not available to the user. It is never silently downgraded to an ordinary chat <br/>• `incognito_session_id` – The session ID you already used when uploading files, so the new session owns those files. Ignored unless `incognito` is true |
| `stream` | Defaults to `true`. If true, Onyx responds with an SSE stream of packets, the same set the Onyx UI uses. You assemble the answer, reasoning tokens, and tool calls from the streamed packets. If false, Onyx returns one `ChatFullResponse` JSON object. |
| `include_citations` | Defaults to `true`. If false, Onyx removes citation markers such as `[1]` from the answer text and does not emit `citation_info` packets. |
| `additional_context` | A string of extra context injected into the LLM call for this request. The model sees it, but Onyx does **not store it** and it does not appear in chat history.<br></br>Use it for request-scoped information such as the user's current page URL or session metadata.<br></br>Pass `null` or omit the field to send no additional context. |
| `origin` | Where the message comes from, for usage reporting. Set it to `api` for scripts and integrations. Other values: `webapp`, `chrome_extension`, `slackbot`, `widget`, `discordbot`, `mobile`. Defaults to `unset`. |

<Note>
  `forced_tool_id` is no longer supported. Requests with a non-null value receive a validation error.
  Use `preferred_tool_id` for an optional preference. Action invocation is not guaranteed.
  Selecting an Action does not grant permission to use it or bypass approval.
  Deep Research does not accept an Action preference. An unavailable Action produces an error.
  Slack also uses a search preference; it does not guarantee a search on every request.
</Note>

### Non-streaming Response

```python
class ChatFullResponse(BaseModel):
    """Complete non-streaming response with all available data."""

    # Core response fields
    answer: str
    answer_citationless: str
    pre_answer_reasoning: str | None = None
    tool_calls: list[ToolCallResponse] = []

    # Documents & citations
    top_documents: list[SearchDoc]
    citation_info: list[CitationInfo]

    # Metadata
    message_id: int
    chat_session_id: UUID | None = None
    incognito: bool = False
    error_msg: str | None = None
    # Not empty when the response returned early to wait for an approval
    pending_tool_approvals: list[ToolApprovalRequest] = []
```

## Tool Approvals

An MCP Action with the **Ask** approval policy does not run until the user approves the call.
Every client of this API must handle approvals. See [Approvals in Chat](/admins/plugins/mcp#approvals-in-chat)
for the policies.

<Warning>
  A client that does not handle approvals cannot answer a request.
  The call does not run until the request times out after 10 minutes,
  and the chat session does not accept new messages until then. Older mobile app builds, Onyx CLI versions,
  and pinned widget versions do not handle approvals. Upgrade them.
</Warning>

### Approval packets

When a call needs approval, the stream sends a `tool_approval_request` packet at the call's placement.
The packet has these fields:

| Field | Description |
|-------|-------------|
| `approval_id` | The ID to send with the decision. |
| `tool_call_id` | The ID of the tool call that waits. |
| `tool_name` | The name of the tool that the model called. |
| `display_name` | The tool name to show to the user. |
| `arguments` | The arguments of the call. Show them to the user before they decide. |
| `expires_at` | The deadline in ISO 8601 UTC. A call with no decision by this time does not run. |

The stream keeps the response open while the call waits. Other calls and heartbeats can continue.
A `tool_approval_resolved` packet with `approval_id` and `outcome` ends each request:

| `outcome` | Meaning |
|-----------|---------|
| `approved` | The user approved the call, and it runs. |
| `approved_for_chat` | The user approved the tool for the chat session, with this request or an earlier one, and the call runs. |
| `rejected` | The user rejected the call. It did not run. |
| `expired` | No decision arrived before `expires_at`. The call did not run. |
| `disabled` | The user approved the call, but the tool became disabled while the call waited. The call did not run. |
| `cancelled` | The call stopped waiting, for example because the answer stopped. |

When you stop the answer, the stream can end with its `stop` packet before the `tool_approval_resolved` packet.
Treat a request with no resolution as ended when its response stops. Ignore an `outcome` that you do not recognize.

### Send a decision

Call `POST /chat/approvals/{approval_id}/decision` with one of these bodies:

- `{"decision": "approve_once"}` approves this call.
- `{"decision": "approve_session"}` approves this call and later calls of the same tool in the chat session.
- `{"decision": "reject"}` rejects this call.

The response contains `approval_id`, `decision` (`APPROVED` or `REJECTED`) and `decided_via`:

| `decided_via` | Meaning |
|---------------|---------|
| `USER` | The user's decision for this call. |
| `SESSION_GRANT` | `approve_session` approved this call, from this request or an earlier request for the same tool in the chat session. |
| `POLICY` | The tool is disabled now, so Onyx saved `REJECTED` for your approval. The `outcome` is `disabled`. |

Only the user who owns the chat session can decide. Other users get a `404`. While the answer runs,
a repeated decision returns `200` with the saved decision.
A `409` means that the request has a different decision or no longer waits,
for example because the API server that ran the answer restarted.

While a call in a chat session waits for a decision,
a new message to that session gets a `409` with the `error_code` `APPROVAL_PENDING`. Send the decision first.
Turns that start from queued messages can also wait for approval.

### Approvals without streaming

With `stream=false`, Onyx does not wait for the decision. When a call needs approval, the response returns at once with:

- `pending_tool_approvals`: every request of the answer that waits for a decision when the response returns,
  with the same fields as the `tool_approval_request` packet
- `message_id`: the ID of the assistant message that waits
- an empty `answer`

The answer continues on the server. Send the decision, then read the answer:

- Read the chat session with `GET /chat/get-chat-session/{chat_session_id}` until the message with `message_id` has its answer, or
- Read the live stream with `GET /chat/chat-session/{chat_session_id}/resume-stream`.

More calls can need approval after the response returns, for example after your decision.
The resume stream shows their `tool_approval_request` packets.
A new message to the session gets a `409` with `APPROVAL_PENDING` while a call waits.

<Note>
  The Slack and Discord bots cannot show approval requests yet.
  Their answers run tools with the **Ask** policy without asking.
  Tools with the **Disabled** policy are not available to them.
</Note>

## Sample Request

<CodeGroup>
  ```python Python expandable
  import requests

  API_BASE_URL = "https://cloud.onyx.app/api"  # or your own domain
  API_KEY = "YOUR_KEY_HERE"

  headers = {
      "Authorization": f"Bearer {API_KEY}",
      "Content-Type": "application/json"
  }

  response = requests.post(
      f"{API_BASE_URL}/chat/send-chat-message",
      headers=headers,
      json={
          "message": "What is Onyx?",
      }
  )

  data = response.json()
  print("Answer:", data["answer"])
  print("Message ID:", data["message_id"])
  ```

  ```bash Shell expandable
  #!/bin/bash

  API_BASE_URL="https://cloud.onyx.app/api"  # or your own domain
  API_KEY="YOUR_KEY_HERE"

  RESPONSE=$(curl -s -X POST "${API_BASE_URL}/chat/send-chat-message" \
    -H "Authorization: Bearer ${API_KEY}" \
    -H "Content-Type: application/json" \
    -d '{
      "message": "What is Onyx?"
    }'
  )

  echo "Answer:" $(echo "$RESPONSE" | jq -r '.answer')
  echo "Message ID:" $(echo "$RESPONSE" | jq -r '.message_id')
  ```
</CodeGroup>

- To get ranked documents without an answer, use the [Search API](/developers/guides/search_api_guide).

- To call your organization's models through Onyx from your own application,
  use the [LLM Gateway](/developers/guides/llm_gateway).
