Plugins connect Onyx agents to the tools that your team uses. With a plugin, an agent can read live data,
such as a Linear issue, or take an action, such as post a Slack reply.

A plugin holds skills. An integration is an MCP server or an app that the agent calls.
Each integration has its own access: your admin makes it available to everyone, or its owner shares it with you.
You turn each integration on, and you connect your account to each integration that needs it.

<Note>
  MCP servers, OpenAPI apps and Craft Apps are integrations. Find them in **Customize → Integrations** in the sidebar,
  and in Chat under **Actions → Integrations**.
</Note>

## Integration types

| Type | What it does | Where you can use it |
| --- | --- | --- |
| **MCP** | Connects to a [Model Context Protocol](https://modelcontextprotocol.io/) server, such as Linear, Notion, or Atlassian | Chat, custom agents, and Craft |
| **OpenAPI** | Calls a REST API that your admin describes with an OpenAPI schema | Chat and custom agents |
| **Craft App** | Lets Craft act as you in Slack, Gmail, Google Calendar, Google Drive, Notion, Linear, GitHub, HubSpot, or Zendesk | Craft only |

For Craft Apps, see [Craft Apps](/overview/core_features/craft_apps).

### Integrations and Onyx knowledge

Integrations and [connectors](/overview/core_features/connectors) give agents different access.

- **Onyx knowledge** is an index of company documents. Onyx applies the source permissions,
  so you find only documents that you can access. Search is read only.
- **Integrations** call the external service live. When you connect your own account,
  the service applies your permissions. The integration can read only what your account can read,
  and it can change content only if your account and your admin allow it.

## Find a plugin

Select **Customize** in the Chat sidebar or the Craft sidebar. Customize has three tabs: **Skills**,
**Integrations** and **Plugins**. It opens on **Skills**. A plugin packages skills that you turn on together.
Each skill that you add comes in its own plugin. You can also [upload a plugin](#upload-a-plugin)
from Claude Code or Codex. A plugin can name the integrations that it needs, but it does not hold them.
Integrations are on the **Integrations** tab. The **Plugins** tab shows each plugin that you can use, in three groups:

| Group | Plugins |
| --- | --- |
| **Created by you** | The plugins that you added, also after you publish them |
| **From your organization** | The plugins that your admin published for the organization |
| **Shared with you** | The plugins that other people added and shared with you |

Each row shows how many skills the plugin holds.
The row of a plugin that needs integrations shows how many of them you can use,
for example **3 of 5 integrations available**. Search by name,
or use the filter to show only the plugins that are on or off.

The **Skills** tab lists each skill, and the **Integrations** tab lists each integration with its state.

<img className="rounded-image" src="/assets/overview/core_features/plugins/member_plugins_directory.webp" alt="The Plugins tab of Customize, with an uploaded plugin that shows 3 of 5 integrations available and skills in the Created by you group"/>

Click a plugin to open it. A plugin that holds only one skill opens that skill. The plugin page has these tabs.
A tab with nothing to show does not appear.

| Tab | What it shows |
| --- | --- |
| **Overview** | The description, the group, the owner, and for an uploaded plugin the version, author, license and the parts that Onyx does not use |
| **Skills** | The skills of the plugin |
| **Integrations** | The integrations that an uploaded plugin needs, each with your state and one action |
| **Versions** | The versions of a plugin that you own or can edit |

## Upload a plugin

You can upload a Claude Code or Codex plugin. Onyx uses two parts of the plugin:

- the skills in `skills/<name>/SKILL.md`,
- the MCP servers in `.mcp.json` or in `mcpServers` of `plugin.json`.

Onyx does not use commands, agents, hooks, LSP servers, output styles, executables (`bin/`), themes or monitors.
The upload shows these parts under **Not used in Onyx**. A plugin with no skill and no MCP server is refused.

<Steps>
  <Step title="Open the upload dialog">
    Select **Customize → Plugins**, then click **Add → Upload plugin**.
  </Step>

  <Step title="Choose the plugin">
    Drop the `.zip` file or the plugin folder, or click to choose it. The plugin must have `.claude-plugin/plugin.json`,
    `.codex-plugin/plugin.json` or `plugin.json` at the root or in one top-level folder.
  </Step>

  <Step title="Check the preview">
    Onyx shows the name, the version, the skills, each integration that the plugin needs with your state,
    the parts that Onyx does not use, and the warnings. If the zip is not valid, the dialog shows the reason.
  </Step>

  <Step title="Save">
    Click **Save**. Onyx opens the plugin page.
  </Step>
</Steps>

A zip that holds a `SKILL.md` and no `plugin.json` is a skill. The dialog shows **This upload is a skill**.
Click **Continue** to add it with the skill flow. See [Craft Skills](/overview/core_features/craft_skills).

### Upload a new version

The name in `plugin.json` decides where the upload goes. The preview shows the result above the skills:

| Preview | Result |
| --- | --- |
| **Updates *name* to v*n*** | You own or can edit a plugin with the same name. The upload becomes its next version. |
| **New plugin: *name*** | No plugin that you own or can edit has this name. Onyx adds a new plugin to your uploads and turns it on, unless another skill that is on has the name of one of its skills. |

To keep the plugin that has this name as it is, select **Save as a New Plugin**.
Onyx then saves the upload as a new plugin with the next free name, for example `eng-toolkit-2`.
A new version does not change whether the plugin is on.

### Integrations that a plugin needs

A plugin never gives access to an integration. Each integration owns its access.
Onyx matches each MCP server of the plugin to an integration by its URL. The scheme and the host are not case sensitive,
and a trailing slash or a default port does not change the match.
The plugin works without the integrations that you cannot use.

The **Integrations** tab of the plugin page shows one state and one action for each integration:

| State | What you see |
| --- | --- |
| **On** | Nothing to do. The agent can use the integration. |
| **Off** | **Turn on** turns the integration on for you, everywhere. |
| **Not signed in** | **Connect** opens the sign-in of the integration. |
| **No access** | **Ask an admin**. The integration is not shared with you. |
| **Turned off** | **Turned off by your admin**. |
| **Not added** | No integration has this URL. If you can add integrations, **Add for your team** opens the **Add an Integration** page with the name and the URL filled in. Other users see **Ask an admin**. |
| **More than one match** | More than one integration has this URL, so Onyx cannot choose. Ask an admin. |
| **Not supported** | **Not supported in Onyx**. The server runs a local command, has no type, has a `${...}` variable in its URL, or has a user name or password in its URL. |

When you turn a plugin on, or save a new plugin, Onyx also turns on each needed integration that you can already use.
Onyx does not sign you in. If an integration that the plugin needs is still not on,
a dialog lists the integrations with their states and actions.

### Turn a plugin on or off

The plugin page has the **Use this plugin** switch in its header. In the **Plugins** tab,
a plugin that is off shows **Turn on**, and the row menu has **Turn on** or **Turn off**.
The default agent uses only the plugins that you turn on.

| Install setting | The switch |
| --- | --- |
| **Required** | Always on. You cannot turn it off. |
| **Installed** | On until you turn it off. |
| **Available** | Off until you turn it on. |

An admin sets the install setting of each plugin in the Organization library.

## Turn an integration on or off

Select **Customize → Integrations**. Each row shows one state:

| State | What you see |
| --- | --- |
| **On** | The switch is on. You can use the integration in Chat and in Craft. |
| **Turn on** | The switch is off. Turn it on to use the integration. |
| **Sign in** | The switch is on, and **Connect** shows. Connect your account to use the integration. |
| **Turned off** | **Turned off by an admin.** Nobody can use the integration until an admin turns it on again. |

An integration that is on is on everywhere: in default Chat and in Craft.
Your admin sets an install setting for each integration. A **Required** integration is always on,
and its switch is locked. An **Installed** integration is on until you turn it off.
An **Available** integration is off until you turn it on. A custom agent uses each integration that it links to,
with the switch on or off, if you have access and are signed in.

Click an integration to open its page, with the tabs **Overview** (the type, the sign-in, the owner, the state,
and the **Use This Integration** switch), **Configuration** (your connection) and **Actions** (how each action runs).

## Connect an integration

The **Configuration** tab of an integration page shows the status of your connection:

| Status | What you see | Who fixes it |
| --- | --- | --- |
| **Connected** | A check mark | Nobody |
| **Not connected** | **Connect** | You |
| **Needs reconnect** | The reason, for example a change to the sign-in settings, and **Reconnect** | You |
| **Not set up** | **Ask your admin** | An admin, or the owner of a personal integration |

<img className="rounded-image" src="/assets/overview/core_features/plugins/member_plugin_mcp_detail.webp" alt="The Actions tab of the Weather API integration with one action set to Allow and one set to Ask with its Always allow switch"/>

To connect:

1. Click **Connect** or **Reconnect**.
2. Do one of these steps:
    - For an OAuth sign-in, sign in with the service in the new tab. The tab closes when the sign-in is done.
      If your browser blocks the new tab, the sign-in continues in the same tab, then Onyx opens the integration again.
    - For an API key, enter the values that the form asks for, then click **Connect**. Only you use these values.

Sign in with the account that the agent should use. The agent acts as that account.
An integration that is not connected gives the agent no actions until you connect it.

### Always allow an action

Your admin sets each action of an integration to **Allow**, **Ask**, or **Blocked**.
An action set to **Ask** asks for your approval in chat.
The **Actions** tab of the integration page lists each action with its setting. If your admin lets users save it,
turn on **Always allow** for an action that asks, and it runs with no prompt. Some actions always ask,
and their switch stays off with the reason. An action set to **Blocked** never runs.

### Disconnect

Click **Disconnect** on an integration that you connected with your own account. Onyx deletes your connection.
The integration stays available to you.

## Add your own integration

If you have the manage actions permission, click **Add → Add integration** in **Customize**.
Onyx opens the **Add an Integration** page. Choose the type, fill in the details, then click **Add**.
Onyx makes a private integration. You are its owner. Only you can use it until you share it.

### Share or publish your integration

Click **...** on the row of a private integration that you own or manage, or on its page:

- Click **Share** to give specific people access. On the Enterprise plan, you can also add groups.
  A share gives use of the integration only. If the integration uses one account for everybody,
  each person with access uses the account that you connected. The dialog tells you so.
- Click **Publish to Org** to make the integration available to the whole organization.
  Only a user with the organization-wide manage actions permission can publish. For other users,
  **Publish to Org** is off. Ask an admin to publish the integration.

## Use integrations in Chat

Click the actions button in the message bar, then select **Integrations**.
The menu lists the integrations of the current agent. Turn an integration on or off for the agent.
Onyx keeps your choice for the agent, so new chats with the agent use it too.
An existing chat in which you did not change an integration or tool also uses the choice for the agent.
A **Required** integration is always on. An integration that needs sign-in shows **Connect** or **Reconnect**.

<img className="rounded-image" src="/assets/overview/core_features/plugins/chat_actions_plugins_flyout.webp" alt="The actions menu in Chat with the Integrations menu open"/>

The agent decides when to call an integration action. To guide it, name the integration or the service in your message.
For example: "Use DeepWiki to explain how the `onyx-dot-app/onyx` repository handles authentication."

If Chat shows **integrations need sign-in**, click it and connect the listed integrations.
Until you connect an integration, the agent does not get its actions. You can continue chatting with other tools.

### Approve tool calls

Your admin sets an approval policy for each MCP tool. When the agent calls a tool with the **Ask** policy,
the answer pauses. An approval card shows **Approval requested** with the tool name and the arguments of the call.
The card shows below the last message of the chat. If more cards wait, they show in the order of the requests.
When you compare models, each card names its model. Select one of these options:

| Option | Effect |
| --- | --- |
| **Approve once** | The call runs with the arguments that the card shows. |
| **Approve for this chat** | The call runs. Later calls of the same tool in this chat run without a card. |
| **Reject** | The call does not run. The agent is told that you rejected the call. |

The request does not expire. It waits until you decide, also when you close the chat or reload the page.
After the answer stops to wait for your decision, you cannot send a new message in the chat.

After your decision, the card becomes a one-line record of the result, and the answer continues.
The record moves to the tool call in the answer. It stays when the answer finishes and when you open the chat again.
If your admin disables the tool before you approve, the call does not run, and the card shows **Disabled**.
If you stop the answer while it runs, Onyx rejects the call, and the card shows **Not approved**.
After the answer stops to wait for your decision, **Stop** is not available. To end the wait, reject the call.

A subagent that works in the background can also ask for approval. Its card names the subagent.
The request waits until you decide, also after the answer that started the subagent finishes or stops.
You can send new messages while it waits. After your decision, the subagent continues in the background.

The Onyx web app, the mobile app, the website widget, and the Onyx CLI show approval requests.
The Slack and Discord bots cannot show approval requests, so they do not get tools that need approval,
except the tools that their agent had before integrations were added. Incognito chats can block approvals,
if your admin sets them to keep no content. There, a tool that needs approval does not run, and the agent is told why.

Tools with the **Allow** policy run without a card. By default, an OpenAPI `GET` operation runs without a card,
and the OpenAPI plugins made before integrations were added keep running without a card.
If your admin sets one of these tools to the **Ask** policy, its calls show a card.
Check the result in the service after a change.

<Note>
  The default agent uses each integration that you turned on.
  A custom agent uses the integrations that the agent builder linked, if you have access to them.
  See [Agents](/overview/core_features/agents).
</Note>
