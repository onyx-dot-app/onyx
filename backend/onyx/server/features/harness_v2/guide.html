The changes we kept

AreaBehavior and purpose
Outer harnessExplicit tools, bounded execution, a request-local evidence store, source citations, and completed/partial/blocked/budget outcomes. A normal final answer ends the turn; a separate finish tool is available but not mandatory.
Completion guidance120 seconds is a soft target, with elapsed time and remaining resources surfaced to the agent. Tool and model timeouts remain enforced. There is no one-search limit.
Answer promptAnswer concisely while covering every part of the question. Remove repetition, not necessary facts. We removed the under-100-words target.
ModelsGPT-5.6 Sol for outer decisions, final answers, query expansion and document selection. Reasoning is explicitly off. Native provider calls were verified in the benchmark.
Search feedbackExpose executed queries, scope, novelty, candidate counts and alternative candidate handles. Cached candidate inspection can avoid a new search. Automatic inferred filters are off in this benchmark; explicit filters and permissions still apply.
Question anchoringKeep the original question as the selection anchor. Pass the current search objective separately. Move that objective before the final user message so existing query-rewrite functions actually receive it.
Hierarchical selectionNominate candidates separately for each query before merging and comparing. This avoids relying only on a global merged cutoff. Final selection is 10 documents; we rejected simply increasing how much the answer model reads.
Selection parserCorrectly parse the ! marker that requests wider context from a promising document. Preserve the document rather than dropping its marked identifier.
Evidence retentionWhen all results fit, retain them. When context is constrained, share prefix space across results and preserve truncation/read-more offsets instead of letting the newest result silently displace earlier ones. This is not semantic memory and cannot guarantee preserving a passage deep in a result.
Budget protectionSearch calls cannot spend the 150k-token answer reserve. Nomination protects another 101,024 tokens for final comparison. The final selector has at most 100k input tokens, limited by actual remaining capacity, with explicit fallback diagnostics. These are spending/context allowances, not generated-output targets or prepaid tokens.
ObservabilityBraintrust traces, per-stage timing, outcomes and usage. The headless evaluator additionally records native provider requests and detailed retrieval diagnostics. Local evaluator artifacts are not browser conversation storage.

What is not enabled

Complementary-search history prompting, record-query prompting, source cards, expanded candidate preparation, document-read mode, extra completion review, higher reasoning, and separate inner answer synthesis are not part of the validated profile. Some code for these experiments remains in research snapshots; that does not mean it should ship.

The headless runner, 500-question datasets, gold answers, official graders, benchmark-user helpers, and per-run observer scripts are evaluation infrastructure, not core chat features.

Progress, citations, final, stop

ONYX_CHAT_HARNESS_V2 defaults off in code. The separate ONYX_CHAT_HARNESS_V2_CHANNELS flag enables a native Responses adapter for the outer model, preserving assistant phase metadata. Internal search retains its existing LLM path. Both are enabled only on this benchmark candidate.

Commentary is user-visible progress, not evidence of completion. A final answer is separate from progress and private reasoning. Pending tools still require execution; cancellation, incomplete responses and budget failures remain explicit outcomes. Missing phase uses a documented compatibility rule. Three consecutive progress-only responses stop as partial rather than looping indefinitely. This is not a limit on searches.

Phase metadata is preserved when replaying prior commentary. Tool evidence continues to be supplied through the harness's bounded state, not native tool-history replay. Ordered output items are inspected before any first-choice flattening. Visible message phases are saved in request metadata; final text alone is the saved answer.

New integration, not part of the full500 score: the channels transport and small phase instruction were added after the reported benchmark. Integration tests establish routing and completion behavior, not a new quality result.

Deep research, attachments, project or incognito chats, multiple model responses, forced-tool requests and requests with extra browser context retain the existing loop. Search must be enabled. These modes need separate integration work. Ordinary v2 turns use internal search; the full general-purpose tool catalog is not integrated yet.

How to bring this into core Onyx gradually

  1. Land the correctness repairs with focused tests: selection-marker parsing and objective handoff. Keep unrelated experimental policies out of those changes.
  2. Extract reusable execution and evidence handling: request-local results, clear partial outcomes, soft duration, budget protection, cancellation and source visibility. Preserve existing auth and document scope.
  3. Integrate the tested search profile behind a feature flag: hierarchical selection, final10, navigation feedback and the concise-complete prompt. Retain a rollback path to the existing loop.
  4. Connect the normal chat experience: streaming progress, final-response rendering, citation interactions, stored conversations and follow-up context. The benchmark candidate now connects the normal chat stream, saved messages, source citations, follow-up context and stop handling. Broader core integration still needs the regression coverage below.
  5. Roll out after regression testing: include conversations, explicit filters, restricted users, concurrent requests, cancellation, empty retrieval and cost limits—not just ERAG correctness.

Try it

Open normal Onyx chat, sign in with your benchmark workspace account, and ask a company question. Ordinary text/search chats use the flagged v2 candidate with Sol and reasoning off. Existing sessions may require a fresh benchmark login because the candidate uses its own authentication cookie. Search progress is delivered during work; final answer text is emitted after inference completes. Source references and messages are saved through normal Onyx chat persistence.
